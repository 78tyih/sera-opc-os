# Developing Products

## 核心原则

先解决一个真实问题，再谈平台与生态。对证据负责，不对 Idea 忠诚。任何新产品、新项目或重要功能都必须按本 Skill 执行；不得直接从想法跳到完整开发。

## 强制顺序

### 1. 创始灵感 × 深度调研

把灵感写成**可被证伪的判断**，不是愿景口号。研究必须同时覆盖：成功参照、邻近参照、组件参照、失败案例、用户现实、技术现实与时机。

必须输出：
- 核心问题与目标用户
- Founder Thesis：为什么值得做、为什么是现在
- Reference Map：成功 / 邻近 / 组件 / 失败案例
- 最小切入点（Wedge）
- 3–5 个关键假设

**Gate：** 没有明确 Wedge，不进入开发。调研只为减少关键未知数，禁止无限研究。

### 2. 交叉评审 × 失败推演

交叉评审不是让多个模型重复评价，而是让不同立场主动攻击方案。至少覆盖：产品反方、技术反方、架构反方、商业/成本反方、可靠性/安全反方、替代方案反方。

必须输出：
- 最危险的假设
- “不能做什么”清单
- Pre-mortem：假设 18 个月后失败，最可能为什么
- **预先承诺的判断阈值：继续 / 调整 / 转向 / 停止的条件**

**Gate：** 没有失败条件，不允许进入 MVP。

### 3. 最小验证（MVP / Proof）

MVP 不是缩小版完整产品，而是用最低成本验证**最核心的因果假设**。Research 回答“理论上为什么应该成立”，MVP 回答“现实中到底是否成立”。

规则：
- 一轮只验证最关键问题
- 优先原型、脚本、人工流程或最小链路
- 禁止 MVP Scope Creep
- 记录真实结果，而不是只展示成功 Demo

### 4. 市场验证 × 触达与分发

按顺序验证：
1. **价值**：用户是否真实需要、重复使用、愿意付出时间或金钱
2. **触达**：视觉、语言、声音、交互、人格与节奏如何最容易被理解和信任
3. **分发**：用户从哪里来，为什么尝试，是否会传播
4. **可持续**：可靠性与 Economics 是否成立，包括失败率、retry、rollback、audit、permission、observability、failure handling、单位任务成本与毛利

禁止在价值尚未成立前，用 A/B、包装或投流掩盖问题。

### 5. 事实决策

每轮验证后必须明确选择，不得默认“继续优化”：
- **扩大（Scale）**：核心假设成立，复制已验证成功
- **调整（Iterate）**：核心方向对，实现方式需要修改
- **转向（Pivot）**：问题真实，但产品形态或切入点错了
- **停止（Kill）**：核心问题/假设不成立，停止投入

## 持续学习与决策记录

每次重大变化必须记录：

```text
原本相信什么？
出现了什么证据？
什么判断被推翻或加强？
因此改了什么？
下一轮验证什么？
```

持续循环：**观察 → 反馈 → 复盘 → 更新 → 再验证。**

## 禁止事项

- Platform before Wedge
- 把多模型共识当作交叉评审
- 把 Demo 当产品
- 没有停止条件就持续开发
- 价值未验证就做大规模触达/分发优化
- 因沉没成本拒绝 Pivot 或 Kill
- 用新增功能替代对核心假设的验证
